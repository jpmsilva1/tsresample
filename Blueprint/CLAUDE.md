# CLAUDE.md — tsresample

Standing rules for every session in this repo, whichever agent tool you use (the file is
named for Claude Code, which loads it automatically; `AGENTS.md` points other tools here).
The collaboration workflow (claiming a step, branches, PRs) is in `CONTRIBUTING.md`.

**First act of every session: read `Blueprint/PROGRESS.md`.** It is the only record of which steps
are done, when, and what comes next. Take your step from it, not from memory or an old
handoff note. **Last act of every step: update it** (status, date, evidence) in the same
PR, following the rules at the bottom of that file.

Read `Blueprint/docs/SPEC.md` §0 (v0.8.0) before writing any code. v0.6.0 specified two formulas that were provably wrong, and v0.7.0
specified φ's control points, the bins, the counts, the bias, the SMOTE generator and the
metric conventions in ways that disagree with R. Knowing which is the difference between
implementing this correctly and re-deriving the same bugs.

**The goal (ADR-0011):** the library matches the **original R algorithms**, quirks
included. The canonical R replication is the instrument we verify against, not a target in
itself. Where the paper and R differ, R is the default; the paper reading is at most an
opt-in flag. Experiment-harness choices never shape `src/`.

## The nine rules

**1 — The spec is the contract.** `Blueprint/docs/SPEC.md` is normative. If the code and the spec
disagree, one of them is a bug; decide which, fix that one, and never let them drift
silently. If you believe the spec is wrong, say so and stop — do not implement your own
version of it.

**2 — Ambiguity is resolved by ADR, never by judgement.** The paper is ambiguous, and
differs from the R code, in many places (SPEC §0). Every one has an ADR (0001–0016). If you
hit a new one, **stop and write ADR-00NN** before writing the code. An implementer who resolves an ambiguity quietly has
produced an unreviewable result, because the next reader cannot tell a decision from an
accident.

**3 — Cleanroom. Never open a quarantined path.** The list is in `Blueprint/docs/PROVENANCE.md` §1:
`UBL`, `uba`, `smogn`, `ImbalanceMetrics`, `IRonPy/src`, `IRonPy/iron`, the vendored
resampler bodies in `Exps.R` (lines ~1700–2450), and the colleague's Python port
(`TSResampStrat_Python/Py_Code/tsresamp/`). This is a licensing boundary, not a
style preference — the library is MIT and the references are GPL. When you need a constant
the paper does not give, run an oracle probe (§Research below). Never "just check how UBL
does it." Your tool-call record is auditable and will be audited at every gate.

**4 — Numbers come from oracles, never from reasoning.** Any claim of the form "φ is X" or
"SERA equals Y" must be backed by a comparison against `Blueprint/tests/fixtures/*.json` or a
recorded artifact: `Blueprint/replication/`, or `Results (Clean)/` in the pinned replication
repo (`Blueprint/docs/REPLICATION.md` §1). Plausibility is not evidence. This rule exists
because two formulas in v0.6.0 were plausible, cited, and wrong — and because v0.7.0's φ
fixture was generated by our own formula, so its gate could not fail. An expected value
our own code produced is not an oracle.

**5 — TDD, in vertical slices.** Red before green. One seam, one failing test, the minimum
code to pass it, repeat. Never write all the tests first and then all the implementation —
bulk tests verify imagined behaviour and go insensitive to real changes. The seams are
fixed and listed in `Blueprint/ops/QUALITY_GATES.md` §2; do not invent new ones without saying so.

**6 — No tautological tests.** A test must not compute its expected value the way the
implementation does. Expected values come from `phi_oracle.json`, from the paper, or from
a worked example whose arithmetic is written out by hand in a comment. If deleting the
implementation and re-deriving it inside the test would make the test pass, it is not a
test.

**7 — One task, one session.** Each node in `Blueprint/ops/TASK_GRAPH.md` is a fresh conversation.
Do not carry context between nodes; the graph's dependency edges exist so that everything
a node needs is either in the repo or in its own brief. A session that has drifted onto a
second node should be stopped and restarted.

**8 — Report failures verbatim.** If tests fail, paste the output. If a gate is red, say
which and by how much. If you skipped a step, say you skipped it. A green summary over a
red run is the most expensive thing you can produce here, because the whole project's
value rests on the numbers being trustworthy.

**9 — Lazy is correct, sloppy is not.** Prefer stdlib over a dependency, one line over an
abstraction, deletion over addition. Do not add an interface with one implementation, a
factory for one product, or config for a value that never changes. But never simplify away
input validation at a trust boundary, error handling, or a documented numerical
convention — those are the parts that make the library worth installing.

## Autonomy

| Tier | Meaning | Nodes |
|---|---|---|
| **AUTO** | Implement, test, and open a PR without checking in. Report at the end. | Nodes whose behaviour a gate fully pins |
| **GATED** | Post your plan and wait for approval. Then implement, then wait for merge approval. | Nodes involving synthesis, a new ADR, a licence question, or a release |

`Blueprint/ops/TASK_GRAPH.md` assigns the tier per node. When in doubt, treat it as GATED — the cost
of an unnecessary check-in is a message; the cost of an unreviewed wrong constant is the
whole replication claim.

**Always GATED regardless of node:** writing a new ADR, changing any published tolerance,
adding a runtime dependency, anything touching `pyproject.toml`'s metadata, and any
release.

## Research procedure (rule 4, in practice)

When you need a value the paper does not state:

1. **State the hypothesis precisely,** as a formula you could implement in five lines.
2. **Find the oracle.** Which recorded file contains the answer as *numbers*?
   `Blueprint/docs/REPLICATION.md` §1 is the index.
3. **Probe.** Implement the candidate, compute it on real data, print it next to the
   recorded value with the ratio.
4. **Read the residual, don't fit it.** A constant ratio means a missing normalisation. A
   *varying* ratio means the convention is wrong — go back to step 1. Never introduce a
   fudge factor to close a gap you do not understand.
5. **Test across regimes.** Confirm on at least three datasets spanning different `%Rare`
   levels before believing it. One dataset is curve-fitting.
6. **Write the ADR** with the evidence table, then the code.

This is the procedure that produced ADR-0001 and ADR-0002. It works, and it is slower than
guessing for exactly one iteration.

## Conventions

- **Python ≥ 3.10.** Full type annotations, `mypy --strict` clean on `src/`.
- **`ruff`** for lint and format. One config block in `pyproject.toml`.
- **Coverage floor: 90 %** on `src/tsresample/`. This number appears exactly once, in
  `Blueprint/docs/SPEC.md` §6, and is read from `pyproject.toml`. If you find a different number in
  another file, that file is the bug.
- **Layering.** `pipeline/` may import Layer 1. Layer 1 may not import `pipeline`, and may
  not import `pandas`. CI asserts both.
- **Errors name the fix.** `ValueError` messages state what was given, what was expected,
  and — where there is a list, such as column names — what was available.
- **Comments explain why, not what.** A comment pointing at an ADR beside a non-obvious
  constant is required; a comment restating the line below it is noise.
- **Git.** Conventional commits. Never commit to `main` directly. Do **not** add a
  `Co-Authored-By: Claude` (or any AI co-author) trailer to any commit in this repo.
  Branch names, step claims and the PR flow are in `CONTRIBUTING.md`.
